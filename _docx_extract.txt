PROMPT 1 — INSTRUCTIONS FOR BUILDING THE KENYA SHIPYARDS LIMITED TASKS MANAGEMENT SYSTEM
1. SYSTEM OVERVIEW
Build a professional, secure, responsive web-based Tasks Management, Monitoring, Assignment, Progress Reporting and Employee Performance Management System for Kenya Shipyards Limited, a shipbuilding and marine engineering company in Kenya.
• Allow authorized users, especially supervisors, managers, team leaders and employees, to register through Google, sign in, access role-appropriate modules and maintain their profile.
• Allow supervisors and authorized managers to create, assign, reassign, monitor, update, review, approve, reject, reopen and soft-delete tasks.
• Allow tasks to be assigned to one employee, multiple employees and, where configured, teams.
• Track priorities, categories, task types, departments, sections, teams, dates, hours, progress, blockers, delays and completion notes.
• Record every meaningful change in immutable task history and system audit logs.
• Generate daily, weekly and monthly progress snapshots and employee performance evaluations.
• Provide dashboards and reports with KPIs, charts, filtering, drill-down and printable/PDF output.
• Provide notifications for assignments, due dates, overdue items, progress reviews, comments and account events.
• Enforce server-side role and permission checks for every sensitive operation; never rely on hidden buttons as security.
• Keep data model, business rules and dropdown values configurable through Google Sheets rather than hard-coding operational dimensions.
2. TECHNOLOGY AND ARCHITECTURE
• Frontend: HTML5, CSS3 and vanilla JavaScript, with Font Awesome icons and Google Fonts (Poppins, Roboto, Montserrat).
• Backend: Google Apps Script server-side functions using SpreadsheetApp, LockService, PropertiesService, Utilities, HtmlService, DriveApp where attachments are configured, and appropriate Apps Script services.
• Database: Google Sheets. Each module writes to its designated sheet/named range and reads only the relevant rows containing data.
• Rendering: Google Apps Script HTML Service with a reusable template shell. Feature pages are injected into the shell as fragments.
• Use asynchronous google.script.run calls for CRUD and report operations; show a processing overlay during server operations.
• Use LockService for ID generation and other multi-user write operations that must be serialized.
• Use soft delete/Record Status for business records unless the prompt explicitly requires permanent deletion.
• Use consistent IDs, timestamps and user context across all modules.

4. AUTHENTICATION — GOOGLE LOGIN
• Do not build traditional username/password authentication.
• Use Google Identity Services (GIS) for the Sign-In experience.
• Verify the Google ID token on the server before accepting the user as authenticated. Validate issuer, audience/client ID, expiration and appropriate claims.
• Use the Google sub claim as the immutable User ID. Never use email as the permanent primary key.
• On first login, create a Pending Approval account and collect/confirm required employment/profile information.
• Only administrators may activate a pending user and assign Employee ID, Department, Job Title, Role, Supervisor and Account Status.
• Pending, Suspended and Disabled users must not access operational modules.
• Revalidate the current authenticated context on sensitive server operations. Never trust role data supplied by the browser.

21. DETAILED TASK BUSINESS RULES
• Progress % must be numeric and constrained from 0 to 100.
• Is Overdue is TRUE when the task is active, the due date has passed in Africa/Nairobi, and completion criteria are not satisfied.
• Days Remaining is the positive difference between Due Date and current Nairobi date for non-overdue active tasks; Days Overdue is the positive difference for overdue tasks.
• Completed Date is populated when the task reaches the configured completion status or approved completion workflow.
• If a completed task is reopened, preserve the historical completed event and clear/recalculate active-state fields as appropriate.
• Primary Assignee must refer to an active Employee record unless an explicit historical/archived exception is supported.
• Number of Assignees must equal the current active assignment count for the task.
• Task Score must be derived from configured performance logic and should not be casually typed into the task form.
• Delay Reason and Blocker should become required when a task is materially delayed or blocked, based on configurable workflow rules.
• Actual Hours should reflect submitted/approved work hours according to the configured update workflow.
• Parent Task ID may be blank for a top-level task; child tasks must reference an existing task.
22. COMMENTS, ATTACHMENTS AND HISTORY
Task comments
• Support chronological task discussion, supervisor feedback and replies using Parent Comment ID.
• Restrict deletion/editing of comments according to role and preserve auditability.
Task attachments
• Use Drive/attachment metadata as configured. Store file metadata in TaskAttachments; do not embed binary data in cells.
• Validate task reference, file type/size constraints, uploader identity and authorization.
• Allow View/Open/Remove metadata actions according to permissions; never break the audit trail when an attachment is removed.
Task history
• Every create, assignment, reassignment, edit, status change, priority change, due-date change, progress update, completion, reopen, delete/archive, approve and reject action must create a history row.
• Do not overwrite historical TaskHistory rows. Treat TaskHistory as immutable.
